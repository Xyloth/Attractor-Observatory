# Attractor Observatory Addendum: Observatory Control Room

## Status

Candidate architectural and implementation proposal for Claude Architect review.

This report proposes a new sidecar module for Attractor Observatory: a visually rich, live, read-heavy **Observatory Control Room**. The Control Room is not a replacement for the scientific engine. It is an observability, steering, communication, and portfolio layer that makes the project’s internal state visible.

The purpose is to let the human principal investigator, AI agents, future collaborators, and external reviewers quickly understand what the project is doing, what has changed, what is failing, what is being built, and where the system is becoming scientifically interesting.

This should be treated as a serious project module, not decorative UI work.

---

# 1. Core thesis

The Attractor Observatory has become too complex to steer by reading every file or every line of code.

It now has multiple worlds, campaigns, audits, falsifiers, builder telemetry, doctrine rules, motif systems, basin-floor geometry, reports, and evolving architectural documents. The project needs a **visual command layer** that turns that complexity into live situational awareness.

The Control Room should answer three questions immediately:

1. What is happening right now?
2. What has changed recently?
3. What does the project currently know, doubt, or need reviewed?

This is not merely a dashboard. It is the cockpit for a research instrument.

---

# 2. Why this is not “just UI”

In traditional software, UI polish often comes late. That assumption does not fully apply here.

For Attractor Observatory, the visual layer has four important functions:

## 2.1 Internal steering

The user does not read every line of code. The user reads reports, audits, tests, failures, and high-level deltas. A Control Room gives the user a way to steer through visual pattern recognition.

It should surface:

* failing tests
* falsifier events
* campaign progress
* AI-agent work
* suspicious deltas
* world status
* motif emergence
* trace activity
* doctrine changes
* risky files/modules
* audit disagreement

## 2.2 Scientific observability

If the project is an observatory, it needs instruments.

The UI should help inspect:

* worlds
* traces
* motifs
* basin-floor geometry
* perturbation outcomes
* falsifiers
* calibration results
* negative-space findings

A visual interface can reveal patterns that are difficult to understand from logs alone.

## 2.3 AI workflow telemetry

The project has a second research layer: how to build complex technical systems with multiple AI agents.

The Control Room should show:

* Claude Builder estimates versus actuals
* Codex audit findings
* Claude Architect campaign designs
* defects caught by each agent
* missed defects
* campaign cycle time
* cost and usage where tracked
* sidecar workflow experiments

This makes the AI-orchestration research visible.

## 2.4 External credibility and portfolio value

The project may be used as a portfolio piece.

A recruiter, hiring manager, collaborator, or technical reviewer may not run the full system. They may only see screenshots, a short demo video, and the README.

A bare-bones useful dashboard communicates less than a polished, information-rich research cockpit.

The design principle should be:

> Usefulness first. Visual impact second. But visual impact is still a first-class deliverable because presentation affects comprehension, credibility, and attention.

The Control Room should look like the front end of a serious research instrument.

---

# 3. Design doctrine

The Control Room should be:

* read-heavy
* branch-isolated
* non-claim-bearing
* visually rich
* information dense
* immediately legible
* safe to build while unattended
* useful to the user
* impressive in screenshots
* honest about uncertainty
* incapable of silently promoting scientific claims

It should not:

* mutate core scientific artifacts
* weaken thresholds
* change campaign results
* promote exploratory outputs to claim-bearing status
* modify world logic
* rewrite trace schemas
* silently ingest external data as truth
* hide failures behind visuals
* turn scientific uncertainty into aesthetic certainty

Key phrase:

> The Control Room may visualize almost everything. It should mutate almost nothing.

# 5. High-level architecture

The Control Room should be a sidecar app that reads project artifacts and renders them into a visual interface.

It should have a clear boundary:

## Input

Read-only access to:

* campaign reports
* telemetry logs
* test results
* builder task logs
* audit reports
* doctrine files
* world registry
* motif registry
* falsifier ledgers
* negative-space ledgers
* basin-floor reports
* trace summaries
* branch/commit metadata
* candidate factory/intake stubs if present

## Output

The Control Room may write only to its own sidecar area unless explicitly approved.

Allowed outputs:

* UI cache
* visualization metadata
* screenshot/demo assets
* local dashboard config
* generated read-only summaries
* Control Room reports
* mock/sample Factory Intake records, if quarantined

Forbidden outputs:

* claim-bearing scientific registry writes
* world modifications
* detector threshold changes
* trace schema changes
* doctrine changes
* promoted biological evidence
* campaign result edits

Suggested boundary:

The Control Room is a viewer and interpreter, not an authority.

# 6. Visual identity

The Control Room should be visually striking without becoming fake sci-fi decoration.

Desired feeling:

* serious research observatory
* mission control
* scientific instrument
* living systems atlas
* AI operations cockpit
* dark, clean, high-contrast
* subtle motion
* dense but legible
* beautiful screenshots

Visual inspiration language:

* orbital command deck
* systems biology atlas
* research instrument console
* neural/network observatory
* cybernetic field station
* scientific cockpit
* living knowledge graph

This should not be a gray admin dashboard.

It should look like something worth opening.

But every visual flourish should carry meaning.

Examples:

* glow indicates activity, risk, novelty, or unresolved status
* pulses indicate live updates or recent changes
* color encodes status, not decoration
* motion indicates transition, flow, or time
* 3D views represent real relationships, embeddings, or structured maps where possible
* uncertainty is visually represented, not hidden

# 10. Read-only first principle

The first version should be strongly read-only.

Allowed:

* read logs
* read reports
* read test outputs
* parse JSON/Markdown artifacts
* render graphs
* generate summaries
* cache UI state
* produce screenshots
* stub factory objects
* produce Control Room report

Not allowed without explicit review:

* modify campaign outputs
* modify trace files
* modify scientific registries
* modify detector thresholds
* modify world implementations
* promote evidence
* change doctrine files
* rewrite architecture docs

This makes it safe for an unattended Claude Builder campaign.

# 11. Factory stub boundary

The Factory Intake Dock should not become the full Research Ingestion Factory during this run.

It may define:

* visual placeholders
* registry previews
* sample records
* schema stubs
* local mock data
* audit lifecycle display
* candidate/promotion distinction
* source-bound extraction doctrine display

It should not:

* perform uncontrolled external crawling
* promote biological claims
* ingest restricted sources
* infer absence from missing evidence
* treat AI-generated entries as truth
* create claim-bearing biology outputs

Recommended language:

> Factory Intake is a quarantined preview of the future evidence ingestion system. All records are exploratory unless explicitly promoted through audited source-bound workflows.

# 14. Visual design system

Suggested design language:

## Color semantics

* green: verified/pass/healthy
* amber: warning/needs review
* red: failed/falsifier/high risk
* blue: active/in progress
* purple: motif/formalism
* cyan: trace/world activity
* gray: unavailable/unknown
* white: claim-bearing/high-confidence text

Use carefully. No meaningless rainbow.

## Motion semantics

* pulse: active process
* slow glow: live monitored item
* flash: recent event
* fade: historical artifact
* orbit/flow: dependency or trace relation
* jitter/noise: uncertainty or instability, if used

## Typography

* large clear status numbers
* readable labels
* compact technical detail
* strong hierarchy
* avoid tiny unreadable science-console text

## Density

The UI should be dense, but layered.

First glance: simple.

Click/drill: detailed.

# 28. Bottom line

The Observatory Control Room should become the visual command layer for Attractor Observatory.
